- 파운데이션 모델(FM): 대규모 데이터셋에서 사전훈련된 대형 딥러닝 신경망, 새 애플리케이션의 빠르고 경제적인 출발점.
- 특징: **적응성**(프롬프트에 따라 NLP/Q&A/이미지 분류 등 다양한 태스크 고정확도 수행) — 기존 ML(특정 태스크 전용)과 차별.
- 적용 분야: 고객지원, 언어번역, 콘텐츠·코드 생성, 카피라이팅, 이미지 분류/생성/편집, 비디오·오디오 생성, 문서추출, 의료, 자율주행, 로봇공학.

### 1. FM 애플리케이션 설계 고려사항

#### 1.1 사전훈련 모델 선택 기준

| 기준 | 설명 |
|---|---|
| 비용 | 훈련 기간/비용 vs 정확도 트레이드오프(예: 98% 정확도·수십만$ vs 97%·수천$) |
| 지연시간 | 실시간 요구 시 추론 속도 중요(예: 자율주행에는 추론이 느린 KNN 등 부적합) |
| 모달리티 | 모달리티별 임베딩 상이, 앙상블로 여러 모델 결합 시 성능↑ |
| 다국어 | 대상 언어로 학습된 모델 선택 |
| 아키텍처/복잡성 | CNN(영상 인식) vs RNN(NLP) 등 태스크별 적합 아키텍처. 파라미터·계층 수↑ → 정확도↑, 계산·데이터 요구량↑ |
| 성능 지표 | 정확도, 정밀도, 재현율, F1, RMSE, MAP(평균정밀도평균, 객체탐지), MAE — 태스크에 맞는 지표 선택(불균형 데이터엔 정확도 부적합) |
| 편향 | 훈련 데이터 편향 완화, 윤리적 결정 필요 |
| 가용성/호환성 | TensorFlow Hub, PyTorch Hub, Hugging Face 등에서 검색, 프레임워크/언어/라이선스/문서/유지보수 여부 확인 |
| 사용자 지정/설명가능성 | 새 계층·클래스 추가 등 확장 가능성, 내부 작동 이해 가능성 |

**해석 가능성 vs 설명 가능성**
- **투명성(해석가능성)**: 계수·공식으로 예측 이유를 수학적으로 설명 가능(선형회귀, 의사결정트리). 파운데이션 모델은 설계상 매우 복잡해 해석 불가(**블랙박스**).
- **설명 가능성**: 더 단순한 모델로 블랙박스를 근사·설명(내부 작동 몰라도 가능). 해석 가능성이 필수 요구사항이면 사전훈련 FM은 최선의 선택이 아닐 수 있음.
- 복잡성↑ → 성능↑ 가능하나 비용↑, 출력 설명 어려움, 하드웨어 제약·유지보수·데이터 프라이버시 등 추가 고려사항.

<br>

#### 1.2 추론 파라미터
- **추론**: 새 데이터 처리 → 예측 생성(프롬프트 입력 → 응답 출력).
- Amazon Bedrock 지원 파라미터: **온도(temperature), 상위 K(top-K), 상위 P(top-P)**(무작위성·다양성 제어), 응답 길이, 페널티, 중지 시퀀스(응답 길이 제한).
- 목표: 다양성·일관성·리소스 효율성의 균형점 → 프로덕션에서 지속 모니터링/조정.

<br>

#### 1.3 프롬프트 강화 & 벡터 데이터베이스 & RAG
- 프롬프트에 내부 DB/벡터 저장소의 도메인 특화 데이터 추가 → **검색 증강 생성(RAG)**.
- **벡터 데이터베이스**: 수학적 표현(임베딩)으로 저장된 구조/비구조 데이터 모음. 임베딩 모델(ML 모델)로 밀도 높은 벡터 생성. 효율적 조회, 데이터 관리, 내결함성, 인증, 액세스 제어, 쿼리 엔진 제공.
- **RAG 구조**: 검색기(retriever, 지식기반 검색) + 생성기(generator, 출력 생성). 훈련 데이터 이외 최신/도메인 지식 접근 가능 → 환각 완화.
- **RAG 흐름**:
  1. 프롬프트

  2. 쿼리 인코더(임베딩)

  3. 벡터DB에서 유사 임베딩 검색·반환

  4. 원 프롬프트와 결합(증강)

  5. LLM 전송

  6. 완성 반환

- **임베딩 저장 AWS 서비스**: Amazon OpenSearch Service/Serverless(벡터 엔진, 시맨틱 검색), Amazon Aurora, Redis, Amazon Neptune, Amazon DocumentDB(MongoDB 호환), Amazon RDS for PostgreSQL(**pgvector** 확장).
- **Amazon Bedrock 지식 기반**: 완전관리형 RAG, FM을 안전하게 회사 데이터에 연결(재훈련 없이 최신 응답).

<br>

#### 1.4 에이전트
- FM은 사전훈련 지식으로 응답 가능하나 항공편 예약 등 실제 태스크(조직별 데이터/워크플로+커스텀 프로그래밍 필요) 수행 불가.
- **Amazon Bedrock용 에이전트**: 완전관리형 AI 기능, 태스크 자동 분류·오케스트레이션, API로 DB 안전 연결, 데이터 수집/구조화/보강 → 정확한 응답·요청 수행. 프롬프트-완성 워크플로와 사용자/FM/외부 데이터·앱 간 상호작용 조정 소프트웨어. 예: 고객의 다음 스쿠버 다이빙 휴가 예약을 처리하도록 도와주는 에이전트.

### 2. 효과적인 프롬프트 엔지니어링 기법 선택

#### 2.1 프롬프트 구성 요소
- 태스크/지침, 컨텍스트, 입력 텍스트(사용 사례에 따라 조합).
- **퓨샷 프롬프팅**: 예제 제공으로 출력 보정. **제로샷 프롬프팅**: 예제 없음.
- **프롬프트 템플릿**: 지침+예제+콘텐츠+질문 조합.
- **사고의 사슬(Chain-of-Thought)**: 복잡한 태스크의 추론을 중간 단계로 분해 → 품질·일관성↑.
- **프롬프트 튜닝**: 프롬프트 텍스트를 훈련 중 최적화된 연속 임베딩 벡터로 대체, 나머지 모델 파라미터는 고정(전체 미세조정보다 효율적).

<br>

#### 2.2 잠재 공간(Latent Space)
- LLM에 인코딩된 언어 지식 — 관계를 캡처한 저장 패턴(통계 데이터베이스에 비유). 예: 스쿠버 휴가 추천 모델을 목적지·다이빙 깊이·가시성·수온 등 데이터로 훈련시켰다면, "매너티와 함께 스노클링을 하고 싶다"는 메시지에 대해 모델이 이 통계 카탈로그(잠재 공간)를 참조해 관련 목적지를 추천.
- 모델은 대규모 텍스트(RefinedWeb, Common Crawl, StarCoder, BookCorpus, Wikipedia, C4 등)로 훈련되며 품질은 다양함(Wikipedia도 항상 정확하진 않음).
- 잠재 공간에 지식이 부족하면 → **환각** 발생(가장 가까운 일치 항목 선택, 통계적으로는 정상 동작). 예: "공룡이 지구를 어슬렁거렸을 때 25피트 아래로 잠수한 최초의 사람이 누구였는가"라고 물으면, 인간은 그 시대엔 아무도 잠수하지 않았을 것이라 추론하지만 모델은 추론하지 않고 컨텍스트를 고려해 확률적으로 단어를 순차 선택해 답을 생성함(통계적으로는 맞지만 사실은 틀릴 수 있음).
- 프롬프트 작성 전 해당 주제의 잠재 공간 한계를 평가하는 것이 고급 프롬프트 엔지니어링의 핵심.

<br>

#### 2.3 프롬프트 엔지니어링 기법 (7가지)
1. 구체적 지침(형식/예제/비교/스타일/어조/길이/컨텍스트 명시)

2. 원하는 동작의 예제 포함(샘플 텍스트/데이터 형식/템플릿/코드/차트)

3. 반복적 실험·테스트

4. 모델 강약점 파악

5. 단순성-복잡성 균형(모호함 방지)

6. 주석으로 컨텍스트 추가(과도한 복잡화 지양)

7. 가드레일 추가

<br>

#### 2.4 위험 및 제한
- **가드레일**: 원치 않는 주제 정의, 차단 단어 설정, 유해/공격 카테고리 임계값 구성, 민감 데이터 입력 필터링.
- **프롬프트 인젝션**: 신뢰할 수 없는 사용자 입력으로 신뢰된 프롬프트를 조작해 악의적 응답 유도.
- **탈옥(Jailbreak)**: 가드레일 등 안전 조치 우회 시도.
- **납치(Hijacking)**: 새 지침으로 원래 프롬프트 변경/조작 시도.
- **중독(Poisoning)**: 유해 지침을 메시지/이메일/웹페이지에 임베딩.
- AWS 지원: Bedrock, Titan 등이 프롬프트 엔지니어링용 API/도구 제공(구성·모니터링·분석).

### 3. FM 훈련 및 미세조정 프로세스

#### 3.1 핵심 요소: 사전훈련, 미세조정, 지속적 사전훈련
- **사전훈련**: 수백만 GPU·컴퓨팅시간·테라~페타바이트 데이터·수조 토큰 필요. 자가지도학습으로 비정형 데이터에서 학습.
- **미세조정**: 지도학습, 레이블링된 예제로 가중치 업데이트, 특정 태스크 성능 개선. **지침 기반 미세조정**: 레이블된 예제로 특정 태스크 개선.

**미세조정 기법 비교**

| 기법 | 설명 | 특징 |
|---|---|---|
| 전체 미세조정 | 모든 파라미터 업데이트 | 성능↑ but **치명적 망각**(다른 태스크 성능 저하) 위험, 메모리/컴퓨팅 비용 큼 |
| PEFT(파라미터 효율적 미세조정) | 원본 파라미터/가중치 고정, 소수 태스크별 어댑터만 훈련 | 컴퓨팅·메모리 절감 |
| LoRA(저순위 적응) | 원 가중치 고정, 각 계층에 훈련 가능한 저순위 행렬 신규 생성 | 대표적 PEFT 기법 |
| 표현 미세조정(ReFT) | 기본 모델 고정, 숨겨진 표현에 태스크별 개입 학습 | 선형 표현 가설 기반(개념=신경망 표현의 선형 부분공간) |
| 멀티태스크 미세조정 | 여러 태스크의 입출력 예제 포함(대량 데이터 필요) | 치명적 망각 완화, 지침 튜닝 모델 생성 |
| 영역 적응 미세조정 | 제한된 영역별 데이터로 적응 | 업계 전문용어 등 특수 도메인 언어 대응. SageMaker JumpStart 지원 |
| RLHF | 강화학습으로 인간 피드백 데이터에 맞춰 미세조정 | 인간 선호도 정렬 |

<br>

#### 3.2 데이터 준비(미세조정용)
- 프롬프트 템플릿 라이브러리 → 지침 데이터셋 → 훈련/검증/테스트 분할.
- **미세조정 순서**:
  1. 프롬프트

  2. 완성 생성

  3. 레이블과 손실 계산

  4. 가중치 업데이트

- 홀드아웃 검증(검증 정확도)+최종 테스트(테스트 정확도).

**AWS 데이터 준비 옵션**

| 요구사항 | 서비스 |
|---|---|
| 로우코드 준비 | SageMaker Canvas(데이터 흐름) |
| 대규모 처리 | Apache Spark/Hive/Presto, SageMaker Studio Classic+Amazon EMR 통합 |
| 서버리스 | AWS Glue 대화형 세션(Spark 기반) |
| SQL 기반 | SageMaker Studio + Jupyter Lab |
| 특성 검색/저장 | SageMaker Feature Store |
| 편향 탐지 | SageMaker Clarify(성별·인종·연령 등 불균형/레이블 편향 탐지) |
| 레이블링 | SageMaker Ground Truth |

<br>

#### 3.3 지속적 사전훈련
- 생성형 AI 출력은 비결정적 → 검증 어려움. 다양한 주제/장르/컨텍스트로 지속 사전훈련하면 모델이 더 강력해지고 영역 외 데이터 적응력↑.
- 예: Amazon Bedrock에서 Titan Text Express/Lite FM을 레이블 없는 고유 데이터로 안전하게 지속 사전훈련.

### 4. FM 성능 평가

#### 4.1 배포 시 고려사항 (1차 질문군)
- 컴플리션 생성 속도, 컴퓨팅 예산, 추론 속도/스토리지 vs 성능 트레이드오프.
- 최적화 기법: 모델 크기 축소(로드 속도↑, 지연시간↓, 성능 저하 가능), 프롬프트 간결화, 검색 코드 조각 크기/개수 축소, 생성 길이 축소.

<br>

#### 4.2 평가 지표/벤치마크
- 결정적 예측(정확도·RMSE)은 계산 단순, 생성형 AI(비결정적)는 태스크별 지표 필요.
- **ROUGE**: 자동 요약/기계번역 평가. **BLEU**: 번역 품질 평가.
- **벤치마크**(태스크 무관 LLM 비교):

  | 벤치마크 | 초점 |
  |---|---|
  | GLUE | 여러 자연어 태스크(감정분석, Q&A) 일반화 성능, 리더보드 |
  | SuperGLUE(2019) | GLUE 확장(다중문장 추론, 독해) |
  | MMLU | 광범위 세계지식·문제해결(역사/수학/법률/컴공 등) |
  | BIG-bench | 현재 모델 한계를 넘는 태스크(수학/생물/물리/편향/언어학/추론/아동발달/SW개발) |
  | HELM | 모델 투명성 개선, 요약/Q&A/감정분석/편향탐지 지표 결합 |

- 인간 평가자 활용(SageMaker JumpStart 모델 응답 비교 등).
- **SageMaker Clarify**: LLM 평가 작업 생성(SageMaker JumpStart 텍스트 FM 품질/지표 비교).
- **Amazon Bedrock 평가 모듈**: 응답 자동 비교, **BERTScore**(인간 참조 대비 시맨틱 유사성) — 충실도·환각 평가에 적합.

#### 4.3 애플리케이션 통합 (2차 질문군)
- 필요 리소스, 외부 데이터/앱 연동 여부와 방법.
- **RAG**: 오래된 내부 지식 문제 해결(재훈련 없이 추론 시 외부 데이터 접근), 복잡한 수학 관련 한계는 여전히 존재. 컨텍스트 제공으로 환각 방지·사실성 개선. 오케스트레이션 라이브러리로 사용자 입력↔LLM 연결·관리.

**엔드투엔드 애플리케이션 스택**

| 계층 | 역할 |
|---|---|
| 인프라 | LLM 제공/호스팅용 컴퓨팅·스토리지·네트워크, 보안(데이터 준비/훈련/추론 전반) |
| 모델+스토리지 | 요구사항에 맞는 LLM 선택, 실시간/거의실시간 상호작용, 사용자 피드백/컴플리션 저장(추가 미세조정용), 데이터 격리 보안 |
| 도구/프레임워크 | LLM용 추가 도구, 모델 허브(중앙 관리·공유) |
| UI/API | 웹사이트/REST API, 보안 연결 |

- 비즈니스 목표 정의 → 성공 지표·지원 인프라 결정 → 지표 측정/모니터링/검토.
