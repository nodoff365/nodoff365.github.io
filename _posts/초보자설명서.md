## 1. 이 인프라가 뭘 하는 건가요?

WordPress로 만든 웹사이트를 사용자들이 끊김 없이 이용할 수 있도록 Azure 클라우드 위에 구성한 서버 환경입니다.

쉽게 말하면, 웹사이트를 안전하고 빠르게 운영하기 위한 **건물 + 보안 시스템 + 비상구**를 만드는 것입니다.

| 비유 | 실제 리소스 |
|---|---|
| 건물 | Web VM, VMSS (서버) |
| 정문 보안 검색대 | Application Gateway + WAF |
| 건물 내부 CCTV | Azure Firewall |
| 경비원 전용 통로 | Azure Bastion |
| 직원 전용 뒷문 | NAT Gateway |
| 금고 | MySQL DB, Storage |
| 비상구 | DR 리전 (Korea South) |
| 본사-지사 전용 전화선 | VPN Gateway |

---

## 2. Hub-Spoke 구조란?

모든 보안 장비를 중심(Hub)에 모아두고, 실제 서비스는 바퀴살(Spoke)에 배치하는 구조입니다.

```
인터넷
  ↓
[Hub VNet] ← 보안 장비 모음 (Firewall, App Gateway)
  ↓ Peering (Azure 내부 전용 고속도로)
[Spoke VNet] ← 실제 서비스 (Web 서버, DB, 스토리지)
```

**없으면 어떻게 되나요?**
모든 리소스가 하나의 네트워크에 섞여 있으면, Web 서버가 뚫렸을 때 DB까지 바로 접근 가능해져요. Hub-Spoke로 분리하면 계층별로 방어선이 생깁니다.

**왜 이 방법을 선택했나요?**
1단계부터 Hub-Spoke 구조를 잡아두면 나중에 Firewall, VPN 등을 추가할 때 구조 변경 없이 리소스만 추가하면 됩니다.

## 3. 단계별 개요

### 1단계 — 뼈대
최소한의 구성으로 웹사이트가 동작하는지 확인합니다.

```
사용자 → 인터넷 → App Gateway → Web VM → MySQL DB
관리자 → Azure Bastion → Web VM (SSH)
Web VM → NAT Gateway → 인터넷 (아웃바운드)
```

### 2단계 — 이중화
서버 하나가 죽어도 서비스가 계속되도록 만듭니다.
- VM 1대 → VMSS (여러 대 자동 확장)
- MySQL 단일 → Zone HA + Read Replica

### 3단계 — 보안 강화
외부 공격을 막고 서비스 상태를 실시간으로 모니터링합니다.
- WAF 활성화 (웹 공격 자동 차단)
- Redis (세션 캐시)
- Azure Monitor (실시간 알림)

### 4단계 — 하이브리드 + DR
두 리전에서 운영하고, 온프레미스 서버와 연결합니다.
- Azure Firewall (모든 내부 트래픽 중앙 통제)
- VPN (Azure ↔ 온프레미스 암호화 연결)
- Korea South DR 리전 (Korea Central 전체 다운 시 자동 전환)

## 4. 주요 리소스 설명

---

### Application Gateway + WAF

**비유: 건물 정문 + 보안 검색대**

모든 사용자 요청이 이곳을 통과합니다. WAF(Web Application Firewall)는 SQL Injection, XSS 같은 해킹 시도를 자동으로 탐지하고 차단합니다.

**없으면 어떻게 되나요?**
사용자 요청이 서버에 직접 들어가고, 해킹 공격을 막을 방법이 없습니다. 악의적인 쿼리로 DB가 통째로 탈취될 수 있어요.

**왜 이 방법을 선택했나요?**
Azure Load Balancer는 단순히 트래픽을 분산하는 L4 장비라 WAF 기능이 없어요. Application Gateway는 L7 장비라 요청 내용을 분석해서 공격을 막을 수 있습니다.

**WAF Detection vs Prevention**

처음엔 Detection 모드로 시작합니다.

```
Detection 모드: 공격 감지 → 통과시키고 로그만 기록 (실제로 막지 않음)
Prevention 모드: 공격 감지 → 즉시 차단
```

WordPress 플러그인 중에 WAF가 공격으로 오인하는 요청을 보내는 경우가 있어요. 바로 Prevention으로 시작하면 정상 플러그인이 차단될 수 있습니다. Detection으로 로그를 먼저 분석하고, 오탐이 없으면 Prevention으로 전환하는 게 안전합니다.

### Azure Bastion vs Jumpbox VM

**관리자가 서버 내부에 접속하는 두 가지 방법 비교**

**Jumpbox VM 방식 (쓰지 않는 이유)**

```
관리자
  ↓ SSH (22번 포트, 인터넷에 공개)
Jumpbox VM (공인 IP 있음)
  ↓ SSH (22번)
Web VM
```

22번 포트가 인터넷 전체에 열려 있어서, 전 세계에서 무차별 대입 공격(아이디/비밀번호를 자동으로 수만 번 시도하는 공격)이 들어올 수 있습니다.

**Azure Bastion 방식 (선택한 이유)**

```
관리자
  ↓ HTTPS (443번, 브라우저로 접속)
Azure Bastion
  ↓ (내부적으로 22번, 외부엔 노출 안 됨)
Web VM
```

브라우저에서 443번으로 접속하면 Azure가 내부에서 알아서 VM에 연결해줍니다. 외부에서 22번 포트를 열 필요가 없어서 무차별 대입 공격 자체가 불가능합니다.

---

### NAT Gateway

**비유: 건물 직원 전용 뒷문 (출구 전용, 입구 없음)**

내부 서버가 소프트웨어 업데이트, 패키지 설치 등을 위해 인터넷으로 나갈 때 사용합니다.

```
Web VM → NAT Gateway → 인터넷 (아웃바운드 가능)
인터넷 → NAT Gateway → Web VM (인바운드 불가능)
```

**없으면 어떻게 되나요?**
서버가 아예 인터넷에 접근을 못 해서 업데이트나 외부 API 호출이 불가능해집니다.

**4단계에서 제거하는 이유**

4단계에서 Web-Subnet에 UDR(트래픽 강제 경로 지정)을 적용합니다. Azure 공식 문서에 따르면 UDR이 NAT Gateway보다 우선순위가 높아서, UDR을 적용하면 NAT Gateway가 있어도 실제로 동작하지 않게 됩니다.

```
4단계 이전: Web VM → NAT Gateway → 인터넷
4단계 이후: Web VM → UDR → Firewall → 인터넷 (NAT GW 무력화)
```

어차피 Firewall이 아웃바운드를 처리할 수 있으니, 동작하지 않는 NAT Gateway를 제거해서 비용($32/월)을 절감합니다.

---

### VMSS (Virtual Machine Scale Set)

**비유: 손님이 많아지면 자동으로 직원이 늘어나는 식당**

평소에는 서버 2대로 운영하다가 접속자가 많아지면 자동으로 서버를 늘리고, 줄어들면 다시 줄입니다.

```
CPU 70% 이상 → 서버 1대 자동 추가
CPU 20% 미만 → 서버 1대 자동 제거
AZ-1, AZ-2 두 곳에 분산 → 한 곳 장애 시 다른 쪽이 서비스 유지
```

**없으면 어떻게 되나요?**
트래픽이 갑자기 몰리면 서버가 버티지 못해 사이트가 다운됩니다. 반대로 한가할 때도 서버를 계속 켜놔야 해서 비용이 낭비됩니다.

**Compute Gallery가 필요한 이유**

VMSS가 서버를 자동으로 늘릴 때, 새 서버에 WordPress와 필요한 소프트웨어를 처음부터 설치하면 시간이 걸립니다. Compute Gallery에 미리 완성된 이미지(골든 이미지)를 저장해두면, 새 서버가 생성되는 즉시 바로 서비스 가능한 상태로 시작할 수 있습니다.

---

### MySQL Flexible Server (VNet Integration)

**비유: 건물 내부 전용 금고**

WordPress의 게시글, 사용자 정보, 설정 등을 저장합니다. 외부 인터넷에서 직접 접근이 불가능하고, 같은 VNet 내부에서만 접근할 수 있습니다.

**VNet Integration 방식이란?**

MySQL Flexible Server는 Private Endpoint 방식이 아닌 VNet Integration 방식을 사용합니다.

```
Private Endpoint 방식: 어디서든 배포 가능 → PE 리소스를 따로 생성해서 VNet에 연결
VNet Integration 방식: 처음부터 위임된 서브넷(MySQL-Subnet) 안에 배치
```

MySQL Flexible Server는 VNet Integration 방식을 사용하기 때문에 MySQL-Subnet을 전용으로 써야 하고, 다른 리소스와 함께 쓸 수 없습니다.

**Zone HA (2단계)**

주 서버가 있는 가용 영역(AZ)에 장애가 발생하면, 다른 AZ에 있는 대기 서버로 자동 전환됩니다. 이 과정이 자동으로 일어나서 서비스 중단 시간이 최소화됩니다.

**Read Replica (2단계)**

게시글 조회, 검색 같은 읽기 요청을 Replica 서버가 처리합니다. 주 서버는 쓰기만 담당해서 부하가 크게 줄어듭니다.

### Redis Cache

**비유: 자주 쓰는 서류를 책상 위에 올려두기 (매번 금고에서 꺼내지 않아도 됨)**

로그인 세션 정보를 빠른 메모리에 저장해서 매번 DB에 묻지 않아도 됩니다.

**Redis와 MySQL의 관계 (중요)**

Redis는 MySQL 앞에서 트래픽을 막는 구조가 아닙니다. 병렬로 연결됩니다.

```
잘못된 이해:
Web → Redis → MySQL (X)

올바른 구조:
Web ├→ Redis  (세션·로그인 정보)
    └→ MySQL  (게시글·상품 데이터)
```

**Session Affinity와의 관계**

2단계에서 App Gateway의 Session Affinity(같은 사용자를 같은 서버로 보내는 기능)를 임시로 활성화했습니다. Redis가 없을 때 VMSS 환경에서 로그인이 유지되도록 하기 위해서입니다.

3단계에서 Redis가 세션을 관리하므로 Session Affinity를 비활성화합니다. 어느 서버로 연결되어도 Redis에서 세션 정보를 가져올 수 있기 때문입니다.

### NSG (Network Security Group)

**비유: 각 층마다 설치된 출입 카드 리더기**

서브넷 단위로 적용되는 방화벽입니다. 허용된 트래픽만 통과하고 나머지는 모두 차단합니다.

**1단계: 기본 규칙**
```
Web-Subnet:   AppGW-Subnet에서 80/TCP, Bastion에서 22/TCP만 허용
MySQL-Subnet: Web-Subnet에서 3306/TCP만 허용
PE-Subnet:    내부 VNet에서만 접근 허용
```

**2단계 정교화**
```
Web-Subnet Inbound 22/TCP
  Source: AzureBastionSubnet (10.1.0.0/26)만 허용
  → 인터넷 전체(0.0.0.0/0)에서 22번 열지 않아도 됨
```

Azure Bastion은 443번으로 외부 접속을 받고, 내부적으로 Bastion 서브넷에서 VM으로 22번 연결을 합니다. 따라서 NSG에서 22번을 허용하되 Source를 AzureBastionSubnet으로 제한하면 인터넷에서의 직접 SSH 접근은 완전히 차단됩니다.

### Azure Firewall

**비유: 건물 내부 모든 통로의 CCTV + 자동 차단기**

4단계에서 배포됩니다. App Gateway가 받은 트래픽이 실제 서버로 가기 전에 Firewall을 통과합니다.

**트래픽 흐름**
```
인터넷
  ↓
App Gateway + WAF (L7 공격 차단, 로드밸런싱)
  ↓
Azure Firewall (내부 트래픽 정책 제어)
  ↓
VMSS (Web 서버)
  ↓
VPN Gateway → 온프레미스 MySQL
```

**App Gateway가 Firewall보다 앞에 있는 이유**

App Gateway v2는 Azure 내부 관리 목적으로 공인 IP가 반드시 필요하고, 인터넷과 직접 통신해야 합니다. Firewall 뒤에 두면 두 가지 문제가 생깁니다.

```
문제 1: 비대칭 라우팅
Firewall → AppGW 요청
AppGW → 응답을 Firewall 거치지 않고 직접 반환
→ Firewall이 "내가 보낸 요청이 아닌데?" 하고 드롭
→ 연결 끊김

문제 2: AppGW 관리 트래픽 차단
AppGW는 Azure가 내부적으로 관리하기 위해 인터넷과 통신이 필요
→ Firewall 뒤에 두면 이 트래픽이 차단되어 AppGW 오작동
```

### VPN Gateway

**비유: 본사(Azure)와 지사(서버실)를 연결하는 암호화 전용 전화선**

Azure와 실제 서버실(온프레미스)을 인터넷을 통해 연결하되, 모든 데이터를 암호화합니다. 외부에서는 내용을 볼 수 없습니다.

**단일 VPN 구성의 위험성 (SPOF)**

현재 VPN을 단일 구성으로 운영합니다. VPN이 끊기면 온프레미스 MySQL에 접근이 불가능해져서 웹사이트 전체가 중단됩니다.

```
VPN 장애 발생
  ↓
VMSS → 온프레미스 MySQL 접근 불가
  ↓
WordPress DB 연결 실패
  ↓
웹사이트 전체 다운
```

**대응 방안 (Q&A용)**

| 방안 | 내용 | 비용 |
|---|---|---|
| Active-Active VPN | VPN을 2개로 운영. 하나 끊겨도 다른 하나로 연결 | +~$140/월 |
| Azure MySQL Replica | VPN 끊겼을 때 Azure MySQL로 자동 전환 | +~$25/월 |
| 온프레미스 회선 이중화 | Bluemax 방화벽에 WAN 회선 2개 연결 | 온프레미스 인프라 비용 |

**VNet Peering Gateway Transit 설정이 중요한 이유**

VPN Gateway는 Hub에 있고 실제 서비스는 Spoke에 있습니다. Spoke에서 온프레미스로 가려면 Hub의 VPN을 빌려 써야 하는데, 이를 위해 Peering 설정에서 반드시 다음을 활성화해야 합니다.

```
Hub → Spoke Peering:   Allow Gateway Transit = true
Spoke → Hub Peering:   Use Remote Gateways = true
```

이 설정이 없으면 Spoke VNet의 Web 서버가 VPN 터널을 통해 온프레미스 DB에 접근할 수 없습니다.

### Private DNS Zone

**비유: 사내 전화번호부**

Storage, Redis에 Private Endpoint를 연결하면 IP 대신 도메인 이름으로 접근합니다. Private DNS Zone이 없으면 "이 도메인 주소가 어디 있는지" 찾지 못해 연결 실패가 납니다.

```
필요한 DNS Zone:
- privatelink.blob.core.windows.net  → Storage 접근용
- privatelink.redis.cache.windows.net → Redis 접근용 (3단계~)
```

**Hub VNet에도 링크해야 하는 이유**

DNS Zone을 Spoke VNet에만 링크하면 Hub에 있는 App Gateway가 백엔드 서버의 도메인 주소를 해석하지 못합니다. Hub VNet에도 반드시 링크해야 합니다.

**4단계에서 South VNet에도 링크하는 이유**

DR 리전(Korea South)이 활성화됐을 때 South의 App Gateway와 Web 서버가 Storage, Redis에 접근하려면 South Hub/Spoke VNet에도 DNS Zone을 링크해야 합니다.

### Storage Account

**비유: 창고 (잠금장치 있음)**

WordPress 미디어 파일, 백업 등을 저장합니다. Private Endpoint로 인터넷에서 직접 접근이 불가능하고, VNet 내부에서만 접근할 수 있습니다.

**LRS → ZRS → GRS 전환 이유**

| 단계 | 복제 방식 | 이유 |
|---|---|---|
| 1단계 LRS | 단일 AZ 내 3개 복사 | 최소 비용 |
| 2단계 ZRS | 3개 AZ에 복사 | AZ 장애 대비 |
| 4단계 GRS | Korea South에 자동 복제 | 리전 전체 장애 대비 |

**GRS 주의사항**

GRS는 데이터를 South에 자동으로 복제하지만, 서비스가 자동으로 South Storage를 읽도록 전환되지는 않습니다. DR 활성화 시 별도의 장애 조치(Failover) 절차가 필요합니다.

## 5. 트래픽 흐름 전체 정리

### 사용자 접속 (1~3단계)
```
사용자 (인터넷)
  ↓ HTTPS
App Gateway + WAF
  ↓ HTTP (백엔드)
VMSS (Web 서버)
  ├→ Redis (세션 확인)
  └→ MySQL (데이터 조회/저장)
```

### 사용자 접속 (4단계)
```
사용자 (인터넷)
  ↓ HTTPS
App Gateway + WAF (L7 공격 차단)
  ↓
Azure Firewall (내부 정책 제어)
  ↓
VMSS (Web 서버)
  ├→ Redis (세션)
  └→ VPN Gateway → Bluemax 방화벽 → MySQL (온프레미스)
```

### 관리자 접속 (전 단계)
```
관리자 (브라우저, HTTPS 443)
  ↓
Azure Bastion
  ↓ (내부 22번)
Web VM / VMSS
```

### 서버 아웃바운드 (1~3단계)
```
Web VM
  ↓
NAT Gateway
  ↓
인터넷 (업데이트, 외부 API)
```

### 서버 아웃바운드 (4단계, NAT GW 제거)
```
Web VM
  ↓ UDR (0.0.0.0/0 → Firewall)
Azure Firewall (SNAT 처리)
  ↓
인터넷
```

## 6. DR (재해 복구) 구조

### 평소
```
Korea Central (ACTIVE): 정상 운영
Korea South (STANDBY):  VMSS min=0 (꺼둠), Storage GRS 복제본만 있음
```

### Korea Central 전체 장애 발생 시
```
1. South VMSS 자동 기동 (min=0 → 스케일 아웃)
2. DNS TTL 만료 후 South App Gateway IP로 전환
3. South VPN Gateway를 통해 온프레미스 MySQL 접근
4. Storage Failover 절차 실행 (자동 아님, 수동 필요)
```

## 7. 비용 설명

| 단계 | 월 비용 | 주요 증가 원인 |
|---|---|---|
| 1단계 | ~$361 | 기본 운영 비용 |
| 2단계 | ~$441 | MySQL Zone HA + Replica (+$50), ZRS (+$10) |
| 3단계 | ~$507 | WAF_v2 (+$35), Redis (+$16), Monitor (+$10) |
| 4단계 | ~$2,700 | Azure Firewall 2개 (~$1,800), VPN GW 2개 (~$280), DR 리전 (~$400) |

**4단계 비용이 갑자기 높아지는 이유**

Azure Firewall은 시간 단위로 요금이 부과되어 월 약 $450/개입니다. 2개이므로 $900 × 2 = $1,800이 고정 비용으로 발생합니다. 보안 인프라는 사용 여부와 관계없이 켜져 있으면 비용이 발생합니다.

**비용 절감 요소 (4단계)**
- MySQL 제거 → -$75/월
- NAT Gateway 제거 → -$32/월
- DR VMSS min=0 → 대기 비용 없음

## 8. 자주 나올 질문 (Q&A 대비)

**Q. VPN이 끊기면 어떻게 되나요?**

A. 온프레미스 MySQL에 접근이 불가능해져 웹 서비스 전체가 중단됩니다. 현재 단일 VPN 구성으로 이 위험을 감수하고 있습니다. 해결책으로는 Active-Active VPN 이중화(+$140/월) 또는 Azure MySQL Replica를 두어 VPN 장애 시 Azure DB로 전환하는 방법이 있습니다.

**Q. WAF Detection과 Prevention의 차이는?**

A. Detection은 공격을 탐지하되 통과시키고 로그만 기록합니다. Prevention은 즉시 차단합니다. WordPress 플러그인 중 WAF가 공격으로 오인하는 경우가 있어 Detection으로 먼저 운영하다가 오탐 없음을 확인하고 Prevention으로 전환하는 것이 안전합니다.

**Q. DR 리전 활성화는 얼마나 걸리나요?**

A. VMSS min=0이라 VM 부팅 시간(약 3~5분)이 필요합니다. DNS 전환 시간(TTL에 따라 최대 5분)을 포함하면 총 5~10분 내 전환됩니다.

**Q. App Gateway가 Firewall보다 앞에 있는 이유는?**

A. App Gateway v2는 공인 IP가 반드시 필요하고 관리 트래픽을 위해 인터넷과 직접 통신해야 합니다. Firewall 뒤에 두면 비대칭 라우팅이 발생해 서비스가 마비됩니다. Azure 권장 패턴은 인터넷 → App Gateway(WAF) → Firewall → Backend입니다.

**Q. MySQL을 온프레미스에 두면 속도가 느리지 않나요?**

A. VPN 터널을 통한 레이턴시가 추가됩니다. Redis가 세션 캐시를 담당하고, Read Replica가 읽기 부하를 분산하므로 실제 DB 직접 접근을 최소화해 영향을 줄입니다.

**Q. Private DNS Zone을 Hub VNet에도 링크하는 이유는?**

A. App Gateway는 Hub VNet에 있습니다. 백엔드 서버의 Private Endpoint 도메인을 해석하려면 Hub VNet에서도 DNS Zone을 찾을 수 있어야 합니다. Spoke에만 링크하면 Hub의 App Gateway가 백엔드 주소를 해석하지 못해 연결 실패가 납니다.

**Q. GRS Storage가 자동으로 South에서 동작하나요?**

A. 데이터 복제는 자동이지만, 서비스가 자동으로 South Storage를 사용하도록 전환되지는 않습니다. DR 활성화 시 Storage Failover 절차를 수동으로 실행해야 합니다.
