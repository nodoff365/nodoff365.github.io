## 1. 프로젝트 개요

Azure 환경에서 발생하는 공격 **행위를 로그 기반으로 탐지하고 자동 대응**하는 체계를 구축한 프로젝트입니다. 인터넷에 노출된 웹 서비스와 내부 데이터베이스로 구성된 환경에서, 외부 공격자가 웹 서버를 거점으로 내부 DB에 침투해 개인정보를 유출하는 **킬체인**을 대상으로 삼았습니다.

공격의 각 단계가 로그로 수집되고 → Microsoft Sentinel 분석 규칙(KQL)으로 탐지되어 인시던트화되며 → 최종적으로 SOAR(Playbook)로 자동 대응되는 전 과정을 설계·구현·검증했습니다. 전체 인프라와 탐지·대응 로직은 Terraform(IaC)으로 코드화하여, 하나의 apply로 배포되는 재현 가능한 통합 환경으로 구성했습니다.

## 2. 수행 환경

### 2.1 시스템 구성

로그 수집 → Sentinel 탐지 → 인시던트 → SOAR 자동 대응으로 이어지는 전체 흐름입니다. 탐지 대상 킬체인은 **외부 정찰(포트 스캔) → 초기 침입(SSH 무차별 대입) → 내부 이동·DB 접근 → 민감 데이터 수집(personal_info 조회) → 권한 상승 시도 → 데이터 유출(mysqldump)** 이며, 각 단계가 로그로 남고 분석 규칙으로 탐지되도록 설계했습니다.

![전체 구성도](/assets/images/Project/azure-behavior-detection-response/architecture.png)
_로그 수집 → 탐지 → 인시던트 → SOAR 자동 대응 전체 구성_

### 2.2 네트워크 설계

역할별 서브넷 분리를 원칙으로 설계했습니다. 관리(bastion)·웹·DB 서브넷을 분리하고, WAF(Application Gateway)와 Azure Firewall은 전용 서브넷을 요구하므로 별도 대역을 확보했습니다. 공격자(Kali)는 **피어링 없는 별도 VNet**에 배치해 실제 외부 공격 환경을 재현했습니다.

| 구분 | 대역 | 용도 |
|------|------|------|
| 메인 VNet | 10.0.0.0/16 | 운영 네트워크 |
| bastion 서브넷 | 10.0.0.0/24 | 관리 접속(점프박스) |
| web 서브넷 | 10.0.3.0/24 | 웹 서버(공인 IP) |
| db 서브넷 | 10.0.5.0/24 | DB 서버(사설 IP) |
| AppGateway 서브넷 | 10.0.6.0/24 | WAF 전용 |
| Firewall 서브넷 | 10.0.7.0/26 | Azure Firewall 전용 |
| Kali VNet | 10.10.0.0/16 | 외부 공격자(분리) |

DB는 사설 IP로만 운영하고 아웃바운드는 NAT Gateway로 처리했습니다. 사설 IP(Web 10.0.3.4, DB 10.0.5.4)는 고정이며, 탐지·대응 로직은 배포 시마다 바뀌는 공인 IP와 무관하게 동일하게 동작합니다.

## 3. 로그 수집 체계

### 3.1 수집 파이프라인

공격 행위를 탐지하려면 먼저 모든 관련 로그를 중앙에 수집해야 합니다. 각 VM의 시스템 로그와 DB 감사 로그를 Azure Monitor Agent(AMA)로 수집하고, DCR(데이터 수집 규칙)이 필요한 facility를 선별해 Log Analytics로 전달하는 파이프라인을 구성했습니다.

> VM(syslog / MariaDB audit) → **AMA** → **DCR** → **Log Analytics(team602-law)** → **Microsoft Sentinel**

### 3.2 수집 대상

| 로그 | Facility | 수집 내용 |
|------|----------|-----------|
| SSH 인증 로그 | authpriv | 로그인 성공·실패, 무차별 대입 |
| MariaDB 감사 로그 | local6 | DB 접속·쿼리·권한 변경·데이터 조회 |
| Apache 접근 로그 | local5 | 웹 스캐너·인젝션 요청 |
| 네트워크 트래픽 | VNet Flow Log | 포트 스캔·횡적 이동 |

### 3.3 수집 검증

Log Analytics에서 각 VM의 로그가 정상 수집됨을 확인했습니다. 먼저 Heartbeat로 web·db VM의 AMA가 정상 통신 중임을 확인하고, Syslog·authpriv·local6 로그가 실제로 유입되는지 점검했습니다.

![Heartbeat 수집](/assets/images/Project/azure-behavior-detection-response/log-heartbeat.png)
_web·db VM Heartbeat 수집 — 에이전트 정상 통신_

![Syslog 수집](/assets/images/Project/azure-behavior-detection-response/log-syslog.png)
_전체 Syslog 수집_

![SSH 인증 로그](/assets/images/Project/azure-behavior-detection-response/log-ssh-auth.png)
_SSH 인증 로그(authpriv) — 정상 로그인과 공격 시도 함께 수집_

![MariaDB 감사 로그](/assets/images/Project/azure-behavior-detection-response/log-mariadb-audit.png)
_MariaDB 감사 로그(local6) — personal_info 조회 쿼리 전문 수집_

특히 공인 IP가 노출된 환경 특성상, 실습 공격 외에도 **실제 인터넷의 SSH 무차별 대입 시도**(외부 IP의 root 접속)가 자동 수집되어, 수집 체계가 실환경 위협까지 포착함을 확인했습니다.

### 3.4 네트워크 레벨 로그 (VNet Flow Log)

호스트 로그로 잡히지 않는 네트워크 계층 행위(포트 스캔·횡적 이동)를 수집하기 위해 VNet Flow Log와 Traffic Analytics를 구성했습니다. team602-vnet 전체 트래픽을 전용 스토리지에 저장하고 Traffic Analytics로 분석해, 출발지·목적지 IP·포트·허용/거부 상태를 네트워크 레벨에서 가시화했습니다.

### 3.5 Defender · 보안 통제 로그 수집

OS 레벨 syslog와 별개로, Defender for Cloud·JIT 등 보안 통제가 남기는 로그도 Log Analytics로 통합했습니다. Defender 데이터는 기본적으로 Defender 포털에만 존재하므로, **연속 내보내기(Continuous Export)**로 Log Analytics에 스트리밍하고, 구독 관리 작업은 Activity Log 진단 설정으로 수집했습니다.

| 로그 | 원천 | 유입 경로 | 테이블 |
|------|------|-----------|--------|
| 보안 권장사항 | Defender 평가 | 연속 내보내기 | SecurityRecommendation |
| 보안 경고 | Defender 탐지 | 연속 내보내기 | SecurityAlert |
| 보안 점수 | Defender | 연속 내보내기 | SecureScore |
| 설정 활동 | 설정 행위 | Activity Log 진단 | AzureActivity |

![Defender 연속 내보내기](/assets/images/Project/azure-behavior-detection-response/continuous-export.png)

![Defender 권장사항 수집](/assets/images/Project/azure-behavior-detection-response/defender-recommendations.png)

## 4. 탐지 체계 (분석 규칙)

### 4.1 규칙 구성

공격 행위를 자동 탐지하는 예약 분석 규칙 **11종**을 Terraform(`azurerm_sentinel_alert_rule_scheduled`)으로 정의했습니다. 시스템·DB 로그 기반, 웹 애플리케이션 로그 기반, 보안 통제 로그 기반으로 구성되며 킬체인 전 단계를 포괄합니다. 각 규칙은 5~10분 주기로 실행되고, 조건 충족 시 인시던트를 자동 생성합니다.

| 규칙 | 심각도 | 탐지 대상 | 출처 |
|------|:---:|------|------|
| SSH Brute Force | Medium | 동일 IP의 SSH 실패 다수 | authpriv |
| 민감정보 접근/유출 | High | personal_info 조회·덤프 | local6 |
| DB 권한 변경/계정 생성 | High | CREATE USER·GRANT 등 | local6 |
| 웹 공격 도구/스캐너 | Medium | nikto·sqlmap·wpscan UA | local5 |
| 웹 인젝션(SQLi/XSS) | High | UNION SELECT·OR 1=1 등 | local5 |
| WAF 웹 공격 차단 | High | AppGW WAF Blocked | AzureDiagnostics |
| Firewall 아웃바운드 차단 | High | Firewall 아웃바운드 Deny | AzureDiagnostics |
| Key Vault 다량 시크릿 조회 | Medium | 단시간 다량 SecretGet | AzureDiagnostics |
| 스토리지 비인가 접근 | Medium | Blob 인증 실패(403/401) | StorageBlobLogs |
| 권한/정책/NSG 변경 | Medium | RBAC·Policy·NSG 변경 | AzureActivity |
| Defender 경고 연동 | High | Defender 보안 경고 | SecurityAlert |

![탐지 규칙 배포 목록](/assets/images/Project/azure-behavior-detection-response/rules-deployed.png)
_배포된 분석 규칙 목록_

### 4.2 KQL 탐지 로직

각 규칙은 탐지 쿼리·심각도·엔티티 매핑(공격자 IP·호스트·계정)·인시던트 생성 설정을 포함합니다. 핵심 탐지 로직은 다음과 같습니다.

- **SSH 무차별 대입** — `sshd` 로그에서 "Failed password / Invalid user"를 추출해 출발지 IP를 파싱하고, **5분 구간 내 실패 10회 초과** 시 탐지
- **민감정보 접근** — local6 로그에서 `personal_info` + `SELECT/SQL_NO_CACHE` 패턴을 DB 계정별로 집계
- **권한 변경** — local6 로그에서 `CREATE USER·GRANT·ALTER USER·DROP USER` 명령 탐지
- **웹 스캐너** — Apache 로그의 User-Agent에서 sqlmap·nikto·wpscan·hydra 등 도구 시그니처 매칭
- **웹 인젝션** — Apache 로그에서 `UNION SELECT·OR 1=1·<script>·information_schema·../..` 등 공격 패턴 매칭

정상 애플리케이션 동작에서는 나오지 않는 패턴을 조건으로 삼아, 정상 트래픽과 공격을 구분하도록 설계했습니다.

## 5. 공격 시나리오별 탐지

외부 공격자가 웹 서버를 거점으로 내부 DB에 침투해 개인정보를 유출하는 공격을 단계별로 수행하고, 각 행위가 Sentinel에서 탐지되는 과정을 검증했습니다.

### 5.1 외부 정찰 (포트 스캔)

공격자가 `nmap`으로 웹 서버 노출 포트를 스캔합니다. 22(SSH)·80(HTTP)·111(rpcbind) 포트 노출을 확인했고, 네트워크 레벨 트래픽이 VNet Flow Log로 수집되어 공격자 IP의 대량 포트 접근이 기록됩니다.

![포트 스캔 탐지](/assets/images/Project/azure-behavior-detection-response/detect-portscan.png)
_포트 스캔 탐지_

### 5.2 초기 침입 (SSH 무차별 대입)

공격자가 `hydra`로 SSH 계정에 무차별 대입을 시도합니다. authpriv 로그에 인증 실패가 기록되고, 동일 출발지 IP의 다수 실패가 Sentinel에서 탐지됩니다.

![SSH 무차별 대입 탐지](/assets/images/Project/azure-behavior-detection-response/detect-ssh.png)
_SSH 무차별 대입 탐지_

![SSH 공격자 IP 집계](/assets/images/Project/azure-behavior-detection-response/detect-ssh-attacker-ip.png)
_SSH 공격 출발지 IP 집계_

### 5.3 내부 이동 · DB 접근

웹 거점을 확보한 공격자가 내부 DB(MariaDB)에 접근을 시도합니다. root 외부 접근은 MariaDB 보안 설정으로 기본 차단되며, 그 시도 자체가 감사 로그에 침해 지표(IoC)로 기록됩니다.

![root 접근 실패 탐지](/assets/images/Project/azure-behavior-detection-response/detect-root-fail.png)
_root 접근 실패 탐지 (FAILED CONNECT)_

### 5.4 민감 데이터 수집

공격자가 애플리케이션 계정(wpuser)으로 개인정보 테이블을 조회합니다. 이름·주민등록번호·연락처·주소를 포함한 50건이 조회되고, 해당 접근이 DB 감사 로그에 기록되어 탐지됩니다.

![민감정보 조회 탐지](/assets/images/Project/azure-behavior-detection-response/detect-sensitive-query.png)
_DB 민감정보(personal_info) 조회 탐지_

### 5.5 권한 상승 시도

공격자가 백도어 계정 생성으로 권한 상승을 시도합니다. wpuser는 권한이 없어 거부(error 1227)되나, 시도 자체가 감사 로그에 기록됩니다. 거부 결과는 최소 권한 원칙이 권한 상승을 차단했음을 보여줍니다.

![권한 변경 시도 탐지](/assets/images/Project/azure-behavior-detection-response/detect-privesc.png)
_권한 변경(계정 생성) 시도 탐지_

### 5.6 데이터 외부 유출 (mysqldump)

공격자가 `mysqldump`로 개인정보 테이블을 덤프합니다. mysqldump는 `SQL_NO_CACHE` 키워드와 함께 전체 컬럼을 조회하며, 이 패턴이 감사 로그에 기록되어 단순 조회와 구분됩니다. 추출 이후의 외부 전송(SCP)은 SSH 키 기반 인증 정책으로 차단됩니다.

![mysqldump 공격 시도](/assets/images/Project/azure-behavior-detection-response/mysqldump-attack.png)
_mysqldump로 personal_info 덤프 시도_

![mysqldump 탐지](/assets/images/Project/azure-behavior-detection-response/mysqldump-detect.png)
_mysqldump 행위 탐지 (SQL_NO_CACHE 패턴)_

### 5.7 웹 애플리케이션 공격 탐지

킬체인(호스트 침투)과 별개로, 외부 공격자가 웹 서버에 직접 수행하는 스캔·인젝션 공격도 Apache 접근 로그(local5)로 탐지합니다. 공격 도구(sqlmap·nikto 등)의 User-Agent와 SQL Injection 패턴(UNION SELECT 등)이 로그에 기록되어, 웹 계층 공격이 Sentinel에서 탐지됩니다. 호스트에 도달한 웹 공격 요청이 Apache 로그로 수집되고, 웹 스캐너·웹 인젝션 규칙에 의해 인시던트로 생성됨을 확인했습니다.

## 6. 인시던트 조사 및 대응

### 6.1 인시던트 자동 생성

위 공격들은 Sentinel 분석 규칙에 의해 공격 후 **약 5분 내에 자동으로 인시던트화**됩니다. SSH Brute Force·민감정보 접근·권한 변경·웹 인젝션·WAF 차단 등 각 시나리오가 규칙별로 탐지되어 인시던트로 생성됨을 확인했습니다.

![인시던트 목록](/assets/images/Project/azure-behavior-detection-response/incident-list.png)
_탐지 경고가 인시던트로 집계됨_

![인시던트 목록 (통합 환경)](/assets/images/Project/azure-behavior-detection-response/incident-list-integrated.png)
_통합 환경에서의 인시던트 생성 확인_

### 6.2 조사 절차

탐지된 인시던트는 다음 절차로 조사합니다.

| 단계 | 활동 | 활용 데이터 |
|------|------|-------------|
| 탐지 확인 | 인시던트 심각도·시각 확인 | SecurityIncident |
| 범위 식별 | 공격자 IP·대상 자산·계정 식별 | 엔티티 매핑 |
| 행위 추적 | 공격 타임라인 재구성 | Syslog, local6 |
| 영향 평가 | 유출 데이터 범위 산정 | personal_info 조회 로그 |
| 대응 | 공격 IP 차단·계정 잠금 | NSG, DB 권한 |

### 6.3 대응 방안

탐지된 위협은 시점별로 세 단계의 대응 체계로 처리합니다.

| 구분 | 대응 내용 |
|------|-----------|
| **즉시 대응** | 공격 IP를 NSG 인바운드에서 차단, 침해 계정 자격증명 변경 |
| **자동화 대응** | 인시던트 발생 시 공격 IP를 NSG에 자동 등록·차단 (7장 SOAR) |
| **사후 조치** | 개인정보 유출 범위 통보, 권한 재설계, 데이터 암호화 적용 |

이 중 반복적·정형적인 "즉시 대응"을 SOAR Playbook으로 자동화하여, 탐지에서 차단까지의 시간을 최소화했습니다.

## 7. SOAR 자동 대응 (Playbook)

### 7.1 구성

탐지에서 그치지 않고, 사람 개입 없이 자동 대응하는 SOAR 체계를 Logic App 기반 Playbook으로 구성했습니다. Consumption 요금제, Korea Central 배포, **트리거 1개 + 액션 3개** 구조입니다.

> Sentinel 인시던트(트리거) → 엔터티에서 공격자 IP 추출 → For each(IP 반복) → web-nsg에 Deny 규칙(Block-Attacker) 자동 생성

| 단계 | 동작 |
|------|------|
| 트리거 | Sentinel 인시던트 생성 |
| IP 추출 | 인시던트 엔터티에서 공격자 IP 획득 |
| 반복 | 추출된 IP 목록을 For each로 순회 |
| 차단 | web-nsg에 해당 IP를 Deny하는 보안 규칙 자동 생성 |

## 8. 결론

OS·DB·네트워크·Apache·Defender 로그를 Log Analytics로 중앙 수집하고, Sentinel 분석 규칙 11종(KQL)으로 포트 스캔·SSH 무차별 대입·DB 접근·민감정보 조회·권한 변경·데이터 유출·웹 공격 등 킬체인 전 단계를 탐지했습니다. 탐지된 인시던트는 SOAR Playbook으로 연결해 공격자 IP를 NSG에 자동 차단함으로써, **로그 수집 → 탐지 → 인시던트 → 자동 대응** 전 과정을 자동화·검증했습니다.

**한계 및 개선 방향**

- **오탐(False Positive) 튜닝** — 실제 운영에서는 정상 행위와의 구분을 위한 임계값·화이트리스트 튜닝이 필요
- **자동 차단의 위험** — SOAR 자동 NSG 차단은 오탐 시 정상 IP를 막을 수 있어, 승인 단계(HITL) 병행 고려
- **탐지 커버리지 확대** — MITRE ATT&CK 기반으로 미탐 구간을 점검·보강
