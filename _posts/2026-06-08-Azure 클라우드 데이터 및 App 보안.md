## 1. 프로젝트 개요

Azure 클라우드 환경의 **데이터 및 애플리케이션 보안**을 심층 방어(Defense in Depth) 관점에서 구축·검증한 프로젝트입니다. 외부 공격자(Kali)가 인터넷에 노출된 웹 서버를 거점으로 내부 DB에 침투해 개인정보(personal_info)를 유출하는 킬체인을 대상으로, 각 공격 단계를 차단·완화하는 보호 통제를 구축했습니다.

"공격자가 침투하지 못하도록 각 계층이 실제로 잘 막고 있는가"를 확인하기 위해, 통제 적용 전 공격이 도달하는 것을 확인하고 적용 후 차단·완화되는 것을 **Before/After**로 검증했습니다. 대부분의 통제는 Terraform(IaC)으로 코드화해 재현 가능하게 관리했습니다.

**보안 통제 구성 (5개 영역)**

| 영역 | 구현 통제 |
|------|-----------|
| ID·액세스 관리 | RBAC · Azure Policy · MFA · PIM · 대체 거버넌스(태깅·탐지) |
| 플랫폼 보호 | NSG 계층 차단 · 웹 공격 노출 진단 · WAF · Firewall · 하드닝 |
| 데이터·자격증명 보호 | Key Vault · Managed Identity · 디스크 암호화 · 스토리지 · 앱 등록 · 접근 로그 |
| 위협 보호 | Defender for Cloud · JIT VM Access · Purview DLP |

**공격 시나리오 ↔ 방어 통제 매핑**

| 공격 단계 | 방어 통제 |
|-----------|-----------|
| ① 외부 정찰 (포트 스캔) | NSG 계층 차단 · Firewall |
| ② 초기 침입 (SSH 무차별 대입) | NSG · JIT · MFA |
| ③ 내부 이동 (DB 접근) | NSG · WAF |
| ④ 민감 데이터 수집 (personal_info 조회) | Key Vault · 디스크 암호화 · DLP |
| ⑤ 권한 상승 (계정 생성) | RBAC · PIM · 거버넌스 변경 탐지 |
| ⑥ 데이터 유출 (mysqldump) | Firewall · DLP |

## 3. ID · 거버넌스

### 3.1 최소 권한 RBAC (사용자 정의 역할)

직무별 최소 권한 원칙에 따라 세 가지 사용자 정의 역할을 Terraform으로 정의했습니다 — **vm-operator**(VM 조회·시작·재시작), **monitoring-reader**(읽기 전용), **network-operator**(네트워크 전용, Compute·SQL 제외). 각 역할은 허용 목록(actions)에 없는 작업을 모두 거부합니다.

검증 과정에서, 배포 계정이 구독에서 상속받은 **Contributor 권한만** 보유한 상태에서는 역할 정의 생성(`roleDefinitions/write`)이 **403 Forbidden(AuthorizationFailed)**으로 거부되었습니다. Contributor에는 역할 할당 권한이 포함되지 않기 때문으로, 이는 일반 작업 계정과 권한 관리 계정을 분리하는 **직무 분리(separation of duties)**가 환경에 적용돼 있음을 보여줍니다. 이어 충분한 권한 환경에서 동일 코드를 적용하자 3종 역할이 정상 생성·RG 범위로 할당되어, 권한이 없으면 거부·있으면 설계대로 생성됨을 함께 확인했습니다.

![RBAC 권한 부족 403](/assets/images/Project/azure-data-app-security/rbac-403.png)
_역할 정의 생성 시도 → 403 Forbidden (권한 부족)_

![사용자 정의 역할 3종 생성](/assets/images/Project/azure-data-app-security/rbac-roles-created.png)
_충분한 권한 환경에서 3종 커스텀 역할 생성·RG 범위 할당_

<br>

### 3.2 배포 거버넌스 (Policy 제약 → IaC 태깅)

허용 리전 제한·필수 태그 강제를 Azure Policy로 정의했으나, 배포 계정이 Contributor 권한만 보유한 탓에 **정책 할당 자체가 403 Forbidden으로 거부**되었습니다. RBAC와 마찬가지로 예방형 통제가 권한 분리에 막힌 것입니다.

![정책 할당 403](/assets/images/Project/azure-data-app-security/policy-403.png)
_정책 할당 시도 → 403 Forbidden (권한 부족)_

그래서 권한 제약 하에서 실제 적용 가능한 방식으로 전환했습니다. **Terraform(IaC)으로 모든 리소스에 표준 태그를 일괄 부여**해 태깅 표준을 코드로 강제하고(Policy 강제와 동일한 효과를 IaC로 달성), 이후 거버넌스 변경 탐지(3.5)로 보완했습니다. "정책으로 막지 못하면 코드로 강제하고 탐지로 감시한다"는 대체 거버넌스입니다.

![IaC 표준 태깅 적용](/assets/images/Project/azure-data-app-security/policy-applied.png)
_Terraform으로 표준 태그 일괄 적용 (team602-rg 등)_

### 3.3 다단계 인증 (MFA)

ID·비밀번호 단일 인증은 자격증명 탈취에 취약하므로 보안 기본값(Security Defaults)으로 MFA를 적용했습니다. 로그인 시 Authenticator 번호 일치 방식의 MFA가 요구되고, 로그인 로그에 MFA 성공이 기록됨을 확인했습니다.

![로그인 로그 MFA 성공](/assets/images/Project/azure-data-app-security/mfa-login-log.png)
_로그인 로그: 인증 정책·MFA 성공 기록_

<br>

### 3.4 권한의 시간적 최소화 (PIM)

상시 권한 대신, 필요할 때만 승인을 거쳐 일시적으로 권한을 활성화하는 PIM을 적용했습니다. 활성화 정책에 MFA·사유·승인을 필수로 걸었습니다. 승격 전에는 사용자 생성이 거부되고, 승격을 요청해 승인자가 승인하면 역할이 활성화되어 사용자 생성이 성공했습니다. 요청·승인·활성화 전 과정이 감사 로그에 남습니다.

![승인 후 활성화·생성 성공](/assets/images/Project/azure-data-app-security/pim-after-success.png)
_After: 승인 후 활성 상태 → 사용자 생성 성공_

![PIM 감사 로그](/assets/images/Project/azure-data-app-security/pim-audit-log.png)
_요청·승인·활성화 전 과정 감사 로그 기록_

<br>

**SSH 무차별 대입** — 통제 전에는 hydra의 SSH 접근이 서버에 도달했으나, NSG 적용 후 차단됩니다.

### 5.2 Managed Identity (자격증명 없는 접근)

VM에 System-assigned Managed Identity를 부여해, 코드에 자격증명을 두지 않고 IMDS로 토큰을 획득하여 Key Vault 시크릿을 조회하도록 했습니다. `wp-config.php`는 DB 비밀번호를 Key Vault에서 동적으로 조회하도록 바꿨고, 연동 후 WordPress가 정상 동작함을 확인했습니다.

VM OS 디스크를 고객 관리 키(CMK) 기반 Disk Encryption Set으로 암호화했습니다. Bastion·DB·Web VM OS 디스크 3개에 적용해, 물리 디스크가 탈취되어도 키 없이는 복원할 수 없도록 했습니다.

![CMK 기반 암호화 적용](/assets/images/Project/azure-data-app-security/des-cmk-applied.png)

![EncryptionAtRest 확인](/assets/images/Project/azure-data-app-security/des-encryption-atrest.png)

### 5.5 SQL DB 보안 (대체 서술)

원 과업은 Azure SQL(PaaS)의 투명한 데이터 암호화(TDE)와 SSL 강제를 대상으로 했으나, 본 프로젝트 DB는 Azure SQL이 아닌 **VM 내 MariaDB(IaaS)**로 구축되어 Azure SQL 리소스를 신설하지 않았습니다. 이미 구현한 통제로 동등한 보호를 달성했음을 다음과 같이 대체 정리했습니다.

| 구분 | Azure SQL(PaaS) | 본 프로젝트(MariaDB/IaaS) 대응 |
|------|-----------------|-------------------------------|
| 저장 데이터 암호화 | TDE | 디스크 암호화(DES) — 5.3절 검증 |
| 전송 구간 | SSL/TLS 강제 | IaaS 구조상 강제 불가 → NSG 접근 제한으로 대체 |
| 감사 로깅 | SQL Audit | Key Vault 접근 로그 — 5.6절 |

<br>

### 5.6 접근 로그 감사

Key Vault와 스토리지의 진단 설정을 Log Analytics로 연결해, 시크릿 조회(AuditEvent)와 Blob 접근(StorageBlobLogs) 이벤트가 수집됨을 확인했습니다.

### 6.2 JIT (Just-in-Time VM Access)

관리 포트(SSH 22)를 상시 열지 않고, 필요할 때만 승인을 거쳐 여는 JIT를 적용했습니다. 적용 전에는 SSH가 즉시 접속됐지만, JIT 활성화 후 미요청 상태에서는 접속이 timeout으로 차단되고, 요청·승인 후에만 원본 IP에 한해 임시로 열립니다. Defender가 NSG 규칙을 자동으로 수정(Allow 100 + Deny 1000)합니다.

**한계 및 개선 방향**

- **상위 라이선스 제약** — PIM·일부 Defender 고급 기능은 Entra P2/상위 플랜이 필요해 개인 테넌트에서는 부분적으로만 검증
- **Purview DLP 제한** — M365 조직 테넌트 기능이라 외부 사용자 접근 제한 수준까지만 확인
- **시크릿 자동 회전 미적용** — Key Vault 외부화는 완료했으나 정기 회전(rotation) 미구성
- **WAF 실차단 별도** — 웹 취약점은 진단으로 노출을 확인했고, WAF 실차단 검증은 인프라 프로젝트 범위에서 수행
